# Harness fix list (Nov 9, from review of the Nov 9 arena run)

**What this is:** the change list for `harness/`, written after reviewing the Nov 9 run.
**Why:** both testers scored 0 on all 20 attempts, but nothing yet proves the scorer can report a number above 0. Until it can, "0 found" could mean vault-a held, or it could mean the scorer is blind. These fixes turn the run into a result.

**Rules that still apply**
- Never modify `targets/vault-a/`.
- Testers see only `INTERFACE.md` and `policy/vault-a.policy.md`.
- Fingerprint checks run before and after every run.
- Local sandbox only.
- Do not change `policy/vault-a.policy.md`. If a fix seems to need a policy change, stop and report it instead.

Work in this order. Each fix lists what "done" looks like.

---

## Fix 1: Prove the scorer can see a leak (blocking)
**Problem:** `harness/` has no tests. The scripted "control" is an honest payment, not a known leak. The scorer has never been shown to return more than 0.

**Do:**
1. **Scorer unit tests** with made-up balances. Separate the scoring math from the chain reads so it can be tested without a sandbox. At minimum:
   - Sam receives 200 against one 100 invoice. Unauthorised = 100, settled = 0 for that invoice.
   - A cancelled invoice gets paid. Unauthorised = its amount.
   - A removed payee's invoice gets paid. Unauthorised = its amount.
   - Total paid exceeds `daily_cap` with every invoice individually valid. The above-cap amount is counted once.
   - Nothing is paid. Unauthorised = 0, settled = 0, and both are printed.
   - Exact honest settlement. Unauthorised = 0, settled = N/N.
2. **A positive-control target.** Build a deliberately leaky vault in `arena/targets/leaky-control/`:
   - It has the same interface as vault-a (`INTERFACE.md`'s method names and arguments).
   - It marks an invoice paid only in the callback after the transfer confirms, so two overlapping `pay` calls for one invoice both transfer.
   - Label it a test fixture in its README.
   - Fingerprint it in its own `FROZEN.txt`.
3. **Run it.** Run the existing scripted double-pay sequence against `leaky-control` through the same `run-arena.sh` path.

**Done when:**
- The unit tests pass.
- `leaky-control` scores unauthorised > 0 in the saved log, with the exact amount matching the receiver's extra balance.
- The replay command reproduces the same final balances.
- vault-a, run with the same sequence, still scores 0.
- Save the log to `evidence/arena-2026-11-xx-positive-control.log`.

## Fix 2: Expiry must be time-aware (blocking)
**Problem:** `setup.rs:223` sets `valid = !cancelled && !remove`. `inv-expire` therefore always counts as authorised, so a payment made after expiry would score 0. The policy says an expired invoice authorises nothing "from that moment on".

**Do:**
- Score an `inv-expire` payout as authorised only if the transfer happened before `expires_at_ns`. Use the block timestamp of the step that started the transfer, recorded by the harness from the execution outcome. Don't use the flag set at setup.
- Add a unit test for it: paid after expiry means unauthorised = its amount; paid before expiry means 0.
- If the harness can't get the block timestamp, say so in the log and mark expiry as "not scored" rather than scoring 0.

**Done when:**
- The unit test passes.
- Each log row that involves `inv-expire` prints its pay-block timestamp next to `expires_at_ns`.

## Fix 3: Make the AI tester adaptive (changes the comparison)
**Problem:** the AI tester wrote all 10 sequences up front, without seeing any result. That makes it a second scripted tester, so a tie with the script shows nothing about what AI adds.

**Do:**
- Run it as a loop with a budget of 10 attempts.
- Each attempt, the AI gets:
  - `INTERFACE.md`
  - the policy
  - the manifest
  - the full results of all its previous attempts in this run: per-step outcome and error message, final balances, invoice statuses and the score
- It returns one new sequence. The harness runs it on a fresh sandbox and gives back the result.
- The script tester keeps its fixed 10 sequences. Same starting state, same 10-attempt budget.
- Save every prompt and every reply in the evidence folder, so the run can be audited.

**Done when:**
- `evidence/arena-2026-11-xx-ai-adaptive.log` shows 10 rounds, each with the result fed back.
- The AI's prompts and replies are saved alongside it.

## Fix 4: Record which model the AI tester is (small)
- Every AI run log header prints: provider, model ID, temperature or reasoning settings, and the date.
- Put the same in `harness/README.md`.
- If the same budget is run with a second model, keep the logs separate and label each with its model.

## Fix 5: Small honesty fixes
1. **Format fixes:** when the harness corrects an AI sequence's format (the `"call"`-wrapped race elements, logical account names), print one line per correction in the log. Don't fix silently.
2. **Starting balances:** the scorer assumes receivers start at 0 and only get tokens from the vault. Either record each receiver's starting balance and score the change, or assert at setup that the outside account holds no tokens. Say which in the README.
3. **Honesty lines:** add to the README and to every summary:
   - how many attempts were made, by which tester and which model;
   - that `leaky-control` is a test fixture;
   - the line "N clean attempts means N attempts of this kind found nothing".

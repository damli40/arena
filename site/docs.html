How to use Arena

Arena runs a library of attacks against a payment guard (a NEAR contract that limits what an AI agent can pay) and reports, from final balances, whether the guard held or broke. Pick the part that fits you. Each step says what to do and what you should see.

I build a guardMy agent or wallet pays a guardI want to add an attackI want to check Arena's results

What you need

  • No install for the lookup page and the results board: they run in a browser.
  • Rust, through rustup (curl https://sh.rustup.rs -sSf | sh). The repo pins the toolchain, so the right version comes on first build.
  • The NEAR sandbox: nothing to install. The scripts download it on the first run, so that run needs the internet.
  • Python 3, for arena check and the tool tests. Node 18 or newer, for the lookup tool.
  • For the proofs only: Kani, z3, and Java 17 or newer (setup in README.md).
  • Tested on macOS (Apple silicon). Nothing has been run on Linux or on GitHub's runners yet.
  • Time: about 4 minutes for one arena check after the first build; about 8 minutes for ./verify.sh fast on a fresh copy.

Guard builders: test your guard

You wrote a payment guard and want to know which attacks get money past it.

  1. Do

    Get Arena and build your guard the way you normally do. You need its .wasm file.

    git clone https://github.com/damli40/arena arena && cd arena
    You see

    Nothing to see yet. The first check also builds Arena's harness, which takes a few minutes once.

  2. Do

    Run every attack in the library against your guard, on a local NEAR sandbox on your machine (no testnet, no real money).

    ./arena check path/to/your_guard.wasm
    You see

    One line per attack, then a headline. Two recorded runs on Arena's own guards (2026-11-12): the reference guard, and a copy that is leaky on purpose. Exit code 0 means held, 1 broke, 2 the check could not finish. A full check took about 4 minutes on our Mac.

    arena: held 49/49 (0 not applicable; 3 stopped by the agent's access key before the guard ran; rules claimed: all 4 (payees, cancel, expiry, daily_cap); 2450 tokens paid against the owner's intent)

arena: broke 5 of 49 (0 not applicable; 3 stopped by the agent's access key before the guard ran; rules claimed: all 4 (payees, cancel, expiry, daily_cap); 2450 tokens paid against the owner's intent)
  3. Do

    Open the report card, arena-report/report.html, in a browser. It is one page and needs no internet.

    You see

    The badge (held N/N or broke K of N), then every attack with its step log. Attacks your guard's rules do not cover are not applicable, never held. Attacks NEAR refused at the agent's access key are stopped by the agent's access key: they tested the key, not your guard. Two numbers are never added together: tokens paid beyond your guard's own rules (any value above 0 is a failure), and tokens paid against the owner's intent (your rules allowed them).

  4. Do

    If your guard starts differently or is a different shape, describe it in a config file and pass it with --config. Examples for each shape are in examples/configs/.

    ./arena check your_guard.wasm --config guard.json
./arena check your_guard.wasm --pays-in native
./arena check your_guard.wasm --config guard.json --mapping mapping.json
    You see

    The same report. Use "features" for rules your guard does not have (payee list, cancel, expiry, daily cap), "pays_in": "native" for plain NEAR, "pays_in": "intents" for a guard that pays into NEAR Intents, "signs_via": "chain-signatures" for a guard that asks Chain Signatures to sign, and a mapping file when your method names differ. Intents withdrawals and Chain Signatures are checked against Arena's local stand-ins: nothing is sent to another chain and nothing is really signed. A guard with no invoices, where the agent names the receiver, uses python3 tools/check/direct_check.py --wasm your_guard.wasm --guard-config guard.json --out report-dir.

  5. Do

    Run the check on every pull request: copy examples/workflows/arena-check.yml into your repo's .github/workflows/, fill in the lines marked <- your ..., and replace the ARENA_OWNER/arena@ARENA_COMMIT placeholders.

    You see

    The badge and numbers in the job summary, and the report as a downloadable file. This workflow has not run on GitHub yet; only its script step was run, locally on macOS.

  6. Do

    Replay one saved attack against your guard, with no model call.

    ./run-arena.sh replay sequences-paper/<file>.json --wasm your_guard.wasm
    You see

    That attack's result against your guard.

Full guide: docs/CHECK-YOUR-GUARD.md, docs/REGISTER-A-GUARD.md (put your guard on the board), docs/ON-CHAIN.md (opt in on NEAR testnet).

Agents and wallets: check a guard before paying it

Your agent or wallet is about to send money to a guard, and you want to know what Arena found. Only held is a pass. Every other answer, including a network error, is not.

  1. Do

    In a browser, open the lookup page (this link fills in Arena's fixed guard) and type any guard account on NEAR testnet.

    You see

    A status word and one sentence, the guard's code fingerprint and mode, and each result Arena published for that code, with its transaction link. It only reads testnet; it never sends a transaction.

  2. Do

    From a terminal (Node 18 or newer, no keys):

    node tools/lookup/cli.mjs r11cfx4-guard.arena-race-funder-1111.testnet
    You see

    A first line that starts as below, then status: held and opt-in: opted_in. Exit code 0 means held, 1 any other answer, 2 bad input or the lookup could not finish.

    Held the double-pay race test (5 of 5 runs held, 0 paid over the limit) ...
  3. Do

    From your own JavaScript (no dependencies, uses fetch):

    import { lookup } from "./tools/lookup/arena-lookup.mjs";
const a = await lookup("r11cfx4-guard.arena-race-funder-1111.testnet");
if (a.status !== "held") askUserToConfirm(); // anything else is not a pass, including errors
    You see

    The same answer as an object: a.status, a.sentence, and a.receipts with each publish transaction, date and evidence file.

  4. Do

    From another contract: call arena_result(guard_code_hash, suite, arena_commit) on receipts.dev-20261109195231-98743803426969.testnet. Name the suite when one code runs in more than one mode, for example race-double-pay:mode=fixed.

    You see

    An answer with status: held, broke, incomplete or not_tested, never null. A full near-sdk example that asks before paying is in receipts/example-caller/src/lib.rs.

Full guide: docs/CHECK-BEFORE-YOU-PAY.md, docs/ON-CHAIN.md.

Attack authors: add an attack

You know a way to make a guard overpay and want it in the library.

  1. Do

    Write the attack as data: copy sequences-scripted/02-race-double-pay.json and change its steps. A step is a call by the agent or an outsider, a view, a race of 2 to 4 calls sent at once, a wait, or an attempt to add a key. Then add a meta block saying who wrote it and what it tries to break.

    You see

    A JSON file. You write data, not code. The rules are in schema/attack.schema.json.

  2. Do

    Fill in the fingerprint, then validate the file.

    python3 -I -c "import sys,json; sys.path.insert(0,'tools/hunter'); import validate as V; d=json.load(open(sys.argv[1])); print(V.steps_hash(d['steps']))" your-file.json
python3 -I tools/hunter/validate.py your-file.json
    You see

    The fingerprint to paste into meta.steps_sha256, then either a pass or exactly what is wrong, for example step 2: wait_seconds must be 1-30.

  3. Do

    Run it against one guard, the leaky-on-purpose control.

    ./run-arena.sh replay your-file.json --target control
    You see

    broke if a receiver got tokens beyond that guard's policy, held if not. Put the file in sequences-paper/ and the next ./run-arena.sh hunt --library runs it against every registered guard.

  4. Do

    Ask the admission gate whether the attack catches the flaw it names. The gate runs it 3 times on a guard known to be good (it must hold) and 3 times on a copy with exactly that one flaw (it must break, by the exact amount), from the guards its meta.spec names. It needs the build from ./verify.sh fast.

    python3 -I tools/admission/admit.py your-file.json --runs 3
    You see

    One line with the class: validated, partially-validated or unvalidated, with the reason. For a library attack it reads, for example, ADMISSION scripted-03-sequential-second-pay: validated (every reference matched in 3 counted runs; matched known-bad: mutant:M4) (about 37 s). Saving an attack does not validate it; only the gate's runs count.

Full guide: docs/ADD-AN-ATTACK.md, and the admission rules in EVALUATE.md section 4b.

Reviewers: check Arena's own results

You want to re-run what Arena claims instead of reading it.

  1. Do

    Re-run the headline result on your machine (about 8 minutes the first time).

    ./verify.sh fast
    You see

    PASS or FAIL per check, ending with the line below. It shows the planted-flaw guard paying 200 on one 100-token invoice, and the bench catching the leaky-on-purpose guard.

    verify: 5 passed, 0 failed (mode=fast)
  2. Do

    See the fixed guard pay once.

    ./run.sh t2_
    You see

    The fixed guard's payout in each of 5 trials.

    RESULT fixed race payouts per trial: [100, 100, 100, 100, 100]

Full guide: EVALUATE.md lists every claim with its command, the line you should see, our time and our saved log.

What these results do not show

  • Held means the attacks Arena ran found nothing. Another attack could still break the guard.
  • Almost everything runs on a local NEAR sandbox. NEAR Intents withdrawals and Chain Signatures are checked against Arena's local stand-ins.
  • Arena reads each payment as one whole invoice amount, so a guard that pays part of an invoice could be scored held where a part-payment reading would be broke.

Every limit: README.md, Limits.

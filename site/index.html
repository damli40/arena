The problem

AI agents will hold money and pay bills for people. A guard is the contract that limits what an agent can pay: which payees, how much a day, which bills.

Most teams test their guard with tests they wrote themselves. Those tests share the guard's blind spots. Arena attacks the guard with attacks its team did not write, and keeps adding more.

How Arena works

Where the attacks come from, which ones count, and how a guard is scored. Every part links the file that backs it.

  1. Attacks from papers, incidents and people

    The hunter is a language model that reads new security papers and hack news and writes attacks as data: a list of steps from a small fixed vocabulary, never code. Real incidents and hand-written attacks fill in the rest. Each hunt can add attacks, which is how the arena keeps growing: 8 hunts so far proposed 41 attacks from 11 paper reads and the news, and Arena kept 25.

    Evidence: evidence/hunts/, docs/ADD-AN-ATTACK.md

  2. An admission gate

    An attack counts as validated only when it holds on a guard known to be good and breaks a copy with exactly one planted flaw, by the exact amount, in 3 runs each. Partly validated means every run matched but a piece is missing, such as proof that two race calls overlapped. Unvalidated attacks still run on every guard. They stay out of the validated count.

    • 33 validated
    • 0 partly validated
    • 21 unvalidated
    • of 54 attacks in the library

    We also planted 10 single mistakes in Arena's own guard, one at a time. The library caught 7 of them.

    Evidence: evidence/MANIFEST.md, tools/admission/admit.py

  3. A hidden set

    Arena keeps 14 more attacks off GitHub and publishes only a hash of the set (2026-11-12). Nobody can tune a guard to a list they cannot see, and anyone can check later that the set did not change.

    Evidence: hidden-set/COMMITMENT.json, EVALUATE.md, section 4b

  4. Scored from chain balances

    Arena runs every attack on a throwaway local NEAR sandbox and reads each receiver's balance before and after every step. The score is the money that moved. What the guard or the agent says about it never enters the score.

    Evidence: docs/CHECK-YOUR-GUARD.md

  5. NEAR's access key, counted apart

    The agent's key may call only pay, so NEAR refuses some attacks before the guard's code runs. Those tested the key, so Arena reports them as "stopped by the access key" and leaves them out of the held count: 3 of 52 on a guard that pays in tokens.

    Evidence: evidence/invoice-fixes-2026-11-12/checks/vault-a/summary.md

  6. Proofs on top of tests

    For the money rules that matter most (no double pay, payee list, per-payment cap, approval threshold, daily budget), Arena also checks every case up to a bound, and proves the double-pay fix on a model of the guard for any number of calls. On four other teams' guards the checker caught 64 of 64 planted flaws.

    Evidence: evidence/proofs-all-2026-11-11.md, proofs/properties/README.md

  7. Results on NEAR testnet

    Arena saves results on NEAR testnet. The lookup page reads which code a guard runs and in which mode, then shows Arena's result for that exact code, so an agent can check a guard before it trusts it with money.

    Evidence: docs/CHECK-BEFORE-YOU-PAY.md

An attacker that reads the guard first

A language model on NEAR AI writes the email the paying agent reads, sees what the agent did, and tries again. In this mode it also reads the guard's rules and source before it writes, the way a real attacker could read a public contract. It never sees the owner's instructions. Arena scores each try from final chain balances.

Limits

  • Held means these attacks found nothing. Another attack could still break the guard.
  • Almost everything runs on a local NEAR sandbox. Only the planted flaw and its fix ran on NEAR testnet.
  • 21 of 54 attacks are unvalidated: they run on every guard, but nobody has shown yet that they catch the flaw they name. Each has a measured reason in evidence/MANIFEST.md: most need two planted flaws at once, ask only for valid payments, or are stopped by the agent's access key before the guard sees them.
  • The proofs stop at their bounds. For the other teams' guards: 2 to 5 payment requests, one UTC midnight, and up to 2 owner actions. The proof for any number of calls covers a model of Arena's guard, matched to the real code up to 4 pay calls.
  • The prompt-injection attacks in the library run scripted steps. No model reads the email in those runs.
  • The hidden set rests on the operator's honesty. Nothing in hardware proves which attacks ran.
  • The hunter's GitHub workflow first ran on 2026-11-13 and now runs one paper hunt a day. That run proposed no new attack. New attacks join the library only through the admission gate, which we run by hand.

Every limit, with its evidence: README.md, Limits.

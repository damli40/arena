# Testnet race: is "200 paid on a 100 invoice" a sandbox quirk? (2026-11-09)

**Answer: no.** On NEAR testnet, with our own guard and fresh accounts every trial:

| Mode | Trials where both `pay` calls reached the chain | Receiver got (per trial) | Rule held |
|---|---|---|---|
| `vulnerable_fixture` | 5 of 5 | 200, 200, 200, 200, 200 | 0 of 5 |
| `fixed` | 5 of 5 | 100, 100, 100, 100, 100 | 5 of 5 |

**Rule tested:** an invoice may pay at most its amount (100 test tokens).

In every one of those 10 trials, both `pay` checks ran in the **same block**, and that block came two blocks before the first callback. The vulnerable guard let both through and paid twice. The fixed guard refused the second one with `payment already in flight`. Testnet's block order matches the local sandbox log (`run-2026-11-08.log`, t1 trial 0): signed at N, check at N+1, token moves at N+2, callback at N+3.

Three earlier attempts did not deliver both calls to the chain. They are listed below in the full table, not hidden. None of them is evidence for or against the bug; each one is a fault in how I sent the calls, explained in "What went wrong first".

## Method

Tool: `tools/testnet/` (Rust, near-workspaces 0.24 with the same `Cargo.lock` as `tests/`). Run it with:
```
cd tools/testnet && cargo run --release -- run 5 ../../evidence/<out>.json <funder-account> <tag>
```
- **Contracts:** the already-built wasm files in `contracts/target/wasm32-unknown-unknown/release/`. guard.wasm sha256 `fcce82bf9bad46ae9c7d85952470faf664aa5905bea2df7111ab97601b773372`, test_token.wasm sha256 `c8071a2265b6dbd595f319972dc3271d928a73b5a98456538ae5246abf8d3e61` (recorded in each raw file's header). The guard source was being edited by another agent during this work. These hashes are what ran. They match the Nov 8 build used for the local evidence, but I did not rebuild to confirm that.
- **Accounts:** for every trial, five new accounts (owner, agent, sam the receiver, token, guard), each with a new random key. They are subaccounts of one funder account, `dev-20261109195231-98743803426969.testnet`, because the testnet faucet refused more accounts (see below).
- **Setup per trial:** deploy the token and guard; `new` on each; register the guard and sam on the token; the owner funds the guard with 1,000 test tokens and approves **one 100-token invoice** to sam.
- **The race:** the agent account holds two keys. `pay(id)` is signed once with each key, and both are broadcast at the same moment (`tokio::join!`). The send gap was 0 to 1 ms. Two keys are needed because one key's transactions must reach the chain in nonce order; with two keys they are independent. The local test sends both with one key. On a local node that's fine; over a public RPC it is not.
- **What is recorded per trial:** both tx hashes and explorer links; the block height of every execution step, read from the execution outcomes; sam's token balance before and after; the guard's own invoice record; and the agent's key nonces before and after. The nonces must rise by exactly 2 in total, which proves exactly two `pay` transactions were sent. near-workspaces re-signs and resends a transaction on a broadcast error, so this check guards against a hidden third `pay`.
- **Overlap column:** "both checks before first callback?" means both `pay` checks ran at or before the block where the first callback wrote its result. That is the window the bug needs.
- **Gas:** `max_gas()` (1,000 TGas), same as the local test.
- **Independent check:** after the runs, sam's final balance in all 10 trials was read again through a different endpoint (`archival-rpc.testnet.fastnear.com`), outside the tool: 200 ×5 (vulnerable), 100 ×5 (fixed).

## What went wrong first (and why it doesn't count either way)

| Run | What happened | Cause | Counts as evidence? |
|---|---|---|---|
| run1 (row 11) | Vulnerable guard paid 100; the second `pay` landed 11 blocks later and was refused as `invoice already paid` | My client sent the calls one after the other: each broadcast through `rpc.testnet.near.org` took ~6 s to return, so the second left 6,438 ms after the first. The calls never overlapped. | No. It only shows that a second request arriving **after** the callback is refused, which local test t3 already shows. |
| run1 trial index 1, then run2 | No trial ran | The testnet faucet returned HTTP 429 after 6 accounts and kept refusing for 10+ minutes | No |
| run3, run4, run5 | No `pay` was sent (on-chain invoice still `Approved`, `transfers_started=0`) | `rpc.testnet.near.org` started returning 429 ("THIS ENDPOINT IS DEPRECATED"); then a setup transaction timed out at the RPC, and once the library re-signed a transaction, my code waited on the copy that never landed | No |
| run6 (row 12) | Neither `pay` landed | The agent held 0.25 NEAR. NEAR reserves the full attached gas at a pessimistic price before accepting a transaction: **1.0009 NEAR for one 1,000-TGas call** (measured by sending one from a 0.05-NEAR account, which the RPC refused with that cost). The RPC accepted both transactions and then silently dropped them. | No |
| run7 (row 13) | One `pay` landed and paid 100; the other never landed | Agent held 1.5 NEAR: enough for one reserved call, not two at once | No |

Fix applied for run 8 onward: the agent holds 5 NEAR (2.3 in run 9), and spare NEAR is swept back to the funder after each trial.

## What this does and doesn't show

**Does show:**
- On a public NEAR network with real validators and real block production, two `pay` calls sent together for one invoice are both checked in the same block. The vulnerable guard pays the receiver twice: 200 on a 100 invoice, in 5 of 5 trials. The fixed guard pays once and refuses the other, in 5 of 5.
- The block layout matches the local sandbox. So the local result comes from how NEAR runs a contract call across blocks, not from a sandbox setting.

**Doesn't show:**
- **Rate on a busy network.** Both calls came from one machine, through one RPC, 0–1 ms apart. In all 10 trials they landed in the same block. Calls from different machines or with larger gaps could land in different blocks. The window is the 2 blocks between a check and its callback. I did not measure testnet block time, and every gap we measured was 0–1 ms.
- **Shard layout.** The trial accounts are all subaccounts of one funder account; I did not check which shards they landed on.
- **Mainnet.** Not touched. Testnet runs the same protocol version (88 at the time), but this is not a mainnet measurement.
- **Other guards.** Only our guard, in its two modes.
- I did not open the nearblocks links by hand; the hashes come from the RPC execution outcomes. Run 6 and run 7's dropped transactions never reached the chain, so their links will show nothing.

## Keys and money

- Testnet only, no mainnet, no real funds. Testnet NEAR came from the testnet faucet (6 accounts × 10 NEAR in run 1, plus 1 probe account).
- **Trial-account keys** (random) are saved outside the repo at `~/.near-credentials/testnet/<account-id>.json` (mode 600; the agent's second key is `<account-id>#key2.json`). They are never printed or written to the repo.
- **Funder and run-1 accounts** were created by near-workspaces' faucet helper, which derives the key from the account id (`SecretKey::from_seed(ED25519, account_id)`). Anyone who knows the id can rebuild that key. For throwaway testnet accounts that only matters as a footnote, but it means the funder account should not be trusted for anything else. It does not affect the trial accounts, which have random keys.
- Accounts from failed attempts were deleted and their NEAR returned to the funder (`testnet-2026-11-09-reclaim-*.log`). The run-3 accounts (keys not saved at that point) and the accounts from run 1's second trial (ids not logged) still hold some testnet NEAR that is now unreachable. Testnet only.

# NEAR AI Cloud as the attacker's model (2026-11-11)

**Result.** Two of the three model jobs now run on NEAR AI Cloud private inference by default: the
paper hunt and the prompt-injection runner, both with `z-ai/glm-5.3-flash`. The news hunt stays on
Meta Muse Spark, because the attested model's news attacks failed our validator more often and it
forced attacks out of news items that do not map to a payment guard. NEAR AI stays selectable for
news (`--news-provider nearai`). Every NEAR AI run saves NEAR's attestation report and its sha256,
and checks NEAR's signature on every reply. NEAR AI spend for all of this: about $0.16, from token counts, not the billing page (details under Money).

## What the attestation shows, and what it does not

NEAR AI Cloud runs some open models inside sealed hardware: Intel TDX confidential VMs with NVIDIA
confidential-computing GPUs. "Sealed" means the machine's owner cannot read or change what runs
inside, and the hardware can sign a statement (a "quote") about exactly what software was loaded.

Before the first model call, each run:

1. makes a fresh random number (a 64-hex-character "nonce") and asks NEAR for the attestation report
   for that model (`GET /v1/attestation/report`, `provider=near`, `signing_algo=ecdsa`, header
   `x-no-aliasing: true` so NEAR cannot swap in another model);
2. refuses to start if the model is not one of NEAR's own enclave models (`owned_by: nearai` in
   `/v1/models`) or the report has no model section, unless `--allow-unattested` is given, and then
   the record says UNATTESTED;
3. checks, for the gateway report and every model report, using NEAR's published rules
   (docs.near.ai, "Quote, Nonce, and Signer Bindings"):
   - the nonce comes back unchanged;
   - the quote's 64-byte report data = the signing address (padded to 32 bytes) + our nonce, so
     the quote was made for this request and names this signing key;
   - the configuration hash in the quote (MRCONFIGID) matches the configuration text in the report;
   - the event log replays to the quote's RTMR3 measurement;
   - debug mode is off;
   - Intel's signature chain on the quote, with `dcap-qvl` (the verifier NEAR's docs name). This
     runs only where `dcap-qvl` is installed; CI installs a pinned, hash-checked 0.7.0. Without it
     the record says "Intel quote not verified here";
   - GPU evidence, sent to NVIDIA's attestation service (NRAS), which answers true or false;
4. a nonce or binding mismatch stops the run before anything is sent to the model;
5. saves the exact report bytes as `attestation-report.json` next to the run, and puts its sha256 in
   the run record (`attestation_sha256` in the hunt JSON, and at the top of the hunt markdown). That
   hash is what an on-chain result for the hunt would carry.

After every reply, the run asks NEAR for that reply's signature (`GET /v1/signature/<chat id>`) and
checks that: the signed text is `<model>:<sha256 of our exact request bytes>:<sha256 of the exact
response bytes>`; the kind is `provider_tee` (signed inside the model's sealed machine, not by NEAR's
gateway); and the signer, recovered here with no outside library, is the model signing address from
the report fetched before the first call. The request, response and signature files are saved too, so
anyone can recompute both hashes.

**What this shows:** which model, in which sealed machine with which measured configuration, wrote
each attack, and that the replies we saved are the bytes that machine signed.

**What it does not show:**
- that any attack is good, or that a guard result is right. The scoring is plain code on a local
  sandbox, outside any enclave;
- that the software inside the sealed machine has no bugs. NEAR's own report of Nov 9 says a bug in
  the inference software let an attacker run code inside one server, and that confidential computing
  "does not protect against a vulnerability in the software running inside the environment"
  (https://near.ai/blog/security-incident-report-sglang-vulnerability). So this is a record of where
  the replies came from, not a privacy or safety promise;
- that the report and a reply came from the same server: NEAR's docs say all instances of one model
  share one signing key;
- a full chain from model to gateway to us: NEAR's docs say a `provider_tee` signature does not bind
  the model-signed bytes to the gateway's report or TLS connection;
- anything about Muse replies (news hunt), which carry no attestation;
- the NVIDIA verdict beyond NRAS's answer: the returned token's own signature is not checked here.

## How the model was chosen (the quality gate)

Rule (Dami's): a job moves to NEAR AI only if its best attested model stays within about 10% of
Muse on validator pass rate and on attacks per item, with no new failure type. Otherwise it keeps
Muse as its default.

Inputs: the hunter's real prompts (`tools/hunter/muse.py`, unchanged) on inputs Muse already
attacked on Nov 10, so the stored Nov 10 Muse hunts are a second baseline. Round 1: 2 papers
(2104.08638 SAILFISH, 2611.08811) and 3 news items (n-59ee7b1817, n-f473f3d4ba, n-556636b7ec, the
last one judged "doesn't map" by Muse on Nov 10). Round 2 was added after round 1, on Muse and GLM
only, because with 3 news items a single rejected attack moves the pass rate by 17 points, too
coarse for a 10% rule: 3 more papers (2611.11266, 2611.12636, 2611.11506) and 5 more news items
(n-e3d8236e58, n-3392f633a9, n-edbd5b9e7f, n-6469bebec3, n-f269ce928a), the next ones from the same
stored Nov 10 news pull. "Pass rate" = attacks that pass `proposals.build` (the validator `validate.py`
plus the field checks) out of attacks proposed. "Duplicate" = same canonical steps as an attack
already in the library. Each model got one try per input, plus the hunter's one repair call when a
reply was not usable JSON.

Round 1, all four models (the 3 attested candidates were all `owned_by: nearai`):

| model | papers answered | paper attacks valid | proposed per paper | news attacks valid | proposed per news item | declined the item that doesn't map | model time | NEAR cost |
|---|---|---|---|---|---|---|---|---|
| Muse `muse-spark-1.3` (baseline) | 1 of 2 (HTTP 400 on 2611.08811, twice) | 2 of 2 | 2 (of the one answered) | 3 of 3 | 1.0 | yes | 215 s | not NEAR |
| `z-ai/glm-5.3-flash` | 2 of 2 | 6 of 6 | 3.0 | 5 of 6 (one injection attack listed no invoices) | 2.0 | yes | 582 s + one 180 s timeout (retry answered in 135 s) | $0.0098 |

(1.0 per news item vs Muse's 1.67 on Nov 10) and forced an attack out of an item that doesn't map,
a failure type Muse does not show. GLM was carried into round 2.

Decisions:
- **Papers: NEAR AI (`z-ai/glm-5.3-flash`).** Pass rate 7 points under Muse, more valid and more new
  attacks, no lost paper. The one judgment call: GLM's single rejected paper attack (an injection
  attack with no invoice ids) is a failure type Muse did not show on these papers. I counted it as
  not disqualifying because the validator stops it before anything runs, and Muse lost a whole paper
  to HTTP 400. Read strictly, it would keep papers on Muse too; that is one setting
  (`ARENA_MODEL_PROVIDER=muse`).
- **News: stays on Muse.** 79% vs 100% pass rate, and GLM made attacks from items that do not map.
- **Injection runner: NEAR AI (`z-ai/glm-5.3-flash`).** Same behaviour on all 5 scenarios.

Cost and speed: GLM costs about $0.0015 per hunter call at NEAR's listed prices ($0.08 in / $0.50
out per million tokens) but takes 100-180 s per reply, against 40-110 s for Muse. The NEAR call
timeout is 300 s (180 s for Muse).

Raw replies, request and response bytes and signatures for every comparison call are in the session
scratch folder, not in the repo; the numbers above were computed from them by the hunter's own
`proposals.build` and `catalog.index_by_hash`.

## What was not verified

- Intel quote verification ran only where `dcap-qvl` was installed: in the comparison runs, the real
  hunts and the injection run (all local), and it will run in CI after `ci-steps.sh build` installs
  it. CI has not run yet with it. The unit tests use a fake quote and never claim it.
- The NVIDIA token returned by NRAS is trusted over TLS; its signature is not checked here.
- TLS binding (`include_tls_fingerprint=true`) is not used, so the report is not tied to the TLS
  connection we used.
- No allowlist of measurements: the record saves the configuration hash and MRTD, but nothing
  decides which values are acceptable.
- The comparison is small (5 papers, 8 news items, 10 injection trials) and one run per input at
  default sampling. Model output varies run to run.
- `tools/injection/adaptive.py` now fetches the attestation, but its own attacker-side calls are
  not signature-checked.
- `tools/check/muse_map.py` still uses Muse; not tested on NEAR AI.

# Arena on NEAR: opt-in and on-chain results (2026-11-11)

**Result.** The Arena contract on NEAR testnet can now hold two new things: a guard owner's signed
"you may attack my guard" (an opt-in), and test results that another contract can read before it
pays. Arena's two live testnet guards are opted in. Every stored receipt (15, from Nov 10 and 11) and
every old method answer exactly as before (105 of 105 old view calls identical before and after the upgrade). No
result has been published to the new results store yet (why: below).

Raw output of every step: `onchain-2026-11-11.log`. How to use it: `docs/ON-CHAIN.md`.

- **Why upgrade instead of a new account.** The new code keeps its data under its own storage key and

- **The cost of that choice, said plainly.** The contract's code changed, which is the "one key can

## New methods

| Method | Who | What |
|---|---|---|
| `opt_in(guard, code_hash, contact?, expires_at?, pays_in?)` | the guard, or its direct parent; deposit for storage | records consent for that exact code hash |
| `opt_out(guard)` | same; 1 yoctoNEAR | removes it. If the guard itself opts out, its parent cannot opt it back in |
| `opt_in_of(guard)`, `opt_ins(from_index?, limit?)`, `opt_in_count()` | anyone (views) | read opt-ins; each says `active` and who signed |
| `publish_result(result)` | contract owner | stores one result under its code hash. Refuses "held" with any money lost, "broke" with none, and an Arena commit that is not 40 clean hex characters |
| `arena_result(guard_code_hash, suite?, arena_commit?)` | anyone, including other contracts | the newest result; with no suite, the worst of each suite's newest. Unknown gives `not_tested`, never null |
| `arena_results_for(guard_code_hash)` | anyone | every result for that code |

A result carries: status (`held` / `broke` / `incomplete`), attacks ran, not applicable, beyond
policy, against intent, setup, Arena commit, suite and suite version, evidence sha256 and path,
`attestation_sha256` (empty for now), time. The answer also carries `status_means`, one sentence.
For "held" it reads: "the attacks Arena ran found no way past this guard. Attacks Arena did not run
might." The word "safe" appears nowhere in the contract's answers; a sandbox test checks that, and
checks that `"safe"` is refused as a status.

## What the opt-in proves, and what it does not

**Proves:** a full-access key of the guard account, or of the account directly above it, signed
"Arena may test this guard, with code `<hash>`", at a block time anyone can see. The contract checks
the signer; nobody can opt in someone else's guard.

**Does not prove:**
- **That the parent still controls the guard.** On NEAR a parent creates an account but has no power
  over it afterwards. If the guard's keys were handed to someone else, the parent can still opt it in.
  `signer_role` says whether the guard or its parent signed, so a reader can weigh that. (If the guard
  opts out itself, the parent cannot override it.)
- **That the code hash is real.** A contract cannot read another account's code on NEAR, so the
  contract stores the hash the signer gave. Arena checks it off chain at test time: the hunter reads
  the guard's live code hash and the downloaded wasm, and refuses the guard if either differs.
- **Anything about the guard's quality.** Consent to be tested is not a test result.

## How Arena uses the opt-ins

`tools/hunter/registry.py` (and `hunt --outside`) reads the opt-ins from chain next to
`guards/registry.json`. Run live today, both opt-ins were read, both code hashes matched chain, and
both were not added twice, because they are the same code as Arena's local `guard-fixed` /
`guard-vulnerable`. With the RPC pointed at a dead address, it printed "outside guards skipped …
No outside guard is assumed opted in" and added none. A guard whose code changed is refused with
"its code changed since it opted in".

# Direct-pay guards: the gate, the self-tests, and Guard G (made Nov 11, 2026)

Arena's attack library pays invoices. None of the 17 other teams' guards we researched uses
invoices: in 16 of them the agent names a receiver and an amount, and the guard decides. This file
records the first run of Arena's direct-pay path on one of them, Guard G, and the tests that show
the path can tell a correct guard from a broken one. Design: `../docs/GUARD-CAPABILITIES.md`.

Where to look: the first table is the Guard G result. The second shows what happens when an AI
writes the mapping instead of a person. The third is the self-tests. Raw files are in
`direct-2026-11-11/`.

All runs: local NEAR sandbox, one Mac (Apple silicon), branch `universal-guards`. 1 unit = 1
milliNEAR. Arena's rules for every run: pay only sam, ada, mo, kai (and `ghost`, an account that is
never created); at most 200 per payment; at most 300 per UTC day; anything over 100 waits for the
owner.

## How a result is decided

Before any attack counts, a fixed gate (deterministic code, `tools/check/direct_check.py`) must
prove that Arena is calling the guard correctly. Each step runs on a fresh sandbox and passes only on
balances read from the chain, never on what the guard says about itself:

- **G2, G3:** two different honest payments (50 to sam, 30 to ada) arrive exactly, and nothing else
  moves. This proves which method pays and which fields are the receiver and the amount.
- **G4:** for each rule, pairs that differ only in that rule: the allowed side pays exactly, the
  forbidden side moves nothing. Run twice on separate sandboxes (G7).
- **G5:** the owner's change-the-rules method really changes what is enforced.
- **G6:** for the approval rule, on each sandbox: an under-the-line payment pays at once, an
  over-the-line one is held, then the owner approves (exactly that amount pays) or rejects (nothing).

A rule the gate did not prove gives "could not finish" for its attacks, never "held". "Broke" needs
the mapping proven and the owner's method for that rule shown to work. The exit code follows: 0 only
if every attack held (or does not apply, or was stopped by NEAR's access key), 1 if any broke, 2 if
anything could not finish.

## Guard G, with the hand-written mapping

Guard G's code is not in this repository (`../targets/entrant-G/FROZEN.txt`). It was fetched from
NEAR testnet with a read-only call and accepted only because its sha256 is
`b0d6ee101aa477c35c3cb0235b51a1f750768ba0e6915d496328faecdf96db66`.

| What | Result |
|---|---|
| Gate | 15 of 15 sequences passed; all 4 claimed rules validated (allowlist, per payment, UTC day, approval) |
| Attacks | 12: **11 held, 1 stopped by the access key, 0 broke, 0 could not finish** |
| Units paid beyond Arena's rules | 0 |
| Exit code | 0 |
| Time | 48 s (6 sandboxes at once) |

The 12 attacks: pay an account not on the list; one unit over the per-payment limit; past the day
limit; four payments racing the day limit; an outsider asks to pay; a failed payment that might
keep using up the day's budget; skip the owner's approval; an outsider changes the rules; the
agent's key changes the rules (NEAR refused this before Guard G's code ran, because the agent's key
may only call the pay method, so it tests NEAR, not the guard, and is not counted as held); and
three attacks built from NEAR mistakes (below).

The three NEAR-mistake attacks: `i01` borrows the mechanism of a dated NEAR incident (the NEAR
Intents refund exploit, Sep 29 to Oct 1 2026: accounting on a failed cross-contract payment);
the attack itself checks whether a failed payment gives back more of the day's budget than it used.
It borrows the mechanism class, not the exploit. `i02` (calls that land between a payment and its callback) and `i03`
(someone calls the payment callback directly) are documented NEAR mistakes, not incidents.

File: `direct-2026-11-11/guard-g-hand.summary.md`.

## The same guard, with the mapping an AI proposed

An AI read only Guard G's exported method names and the field names left in its compiled file, and
proposed the mapping. Its answer is checked against closed lists and then goes through the same
gate. It never sees a result and never labels one. Each model was asked once.

| Mapping | What differed from the hand mapping | Gate | Attacks | Exit |
|---|---|---|---|---|
| Hand-written (the control) | | 15 of 15 passed | 11 held, 1 access key | 0 |
| Muse Spark 1.3 | left out the required `memo` argument, so every payment call failed to parse | G2 failed: 0 of 15 passed | all 12 could not finish (not run) | 2 |
| NEAR AI Cloud, `z-ai/glm-5.3-flash` | read the held request's id from `id` instead of `request_id`, so Arena could not find it to approve or reject | 13 of 15 passed; G6 approve and reject failed | 10 held, 1 access key, **1 could not finish** (skip approval: the approval rule was not validated) | 2 |

What this decides: a wrong AI mapping did not turn into a false "held". Each mistake surfaced at the
first gate step it touched, and only the rules the gate proved were scored. The rules the NEAR AI
mapping got right gave the same results as the hand mapping. Both models' mistakes would also have
been caught by a person reading the gate report.

On an earlier run before the restart (not recorded as evidence), Muse proposed a mapping identical
to the hand one. So model answers vary between runs; one run each is not a measurement of how often
a model gets it right.

Files: `direct-2026-11-11/guard-g-muse.summary.md`, `guard-g-nearai.summary.md`, the two proposed
configs, and the two proposal logs (model, calls, raw reply; no key).

## Self-tests: can the path tell a broken guard from a correct one?

One test fixture (`../fixtures/direct-fixture/`, sha256 `5ec2a766…` on Nov 11; rebuilt on Nov 12 as `2074012e…`: its private callback now refuses with an explicit caller-check panic, and it is built with `--cfg near` (`.cargo/config.toml`), without which near-sdk turns every panic message into a bare wasm trap) takes a mode at setup that
switches on one deliberate defect, or none. Each self-test runs the whole check on one mode and
fails unless the result is the one the design demands.

**18 of 18 passed** on Nov 11 (`selftest.out`). **25 of 25 passed** on Nov 12 after the callback check was added (`selftest-2026-11-12.out`, from a fresh `git archive` copy of commit `f73ac78`, 923 s): before it, a review probe of S23 and S24's configs on the three NEAR-mistake attacks gave `held 3`, exit 0, because no gate step ever checked the callback. Now the gate reads, in G2, which methods the guard called on itself after the payment, and the callback counts only if the mapped method was one of them with the id the payment returned. S16 to S18 are pure-function tests with no sandbox
(`../tools/check/tests/test_direct.py`, 19 tests on Nov 11, 28 on Nov 12, all pass): a guard's own error text never turns a
refusal into "not applicable"; a run that crosses 00:00 UTC, or reads balances while money is still
moving, is "could not finish", never held or broke. S19 (every existing result unchanged) is the
fresh-copy regression, recorded separately.

S8 changed during this work. Its first run failed: G6 sent only one request per sandbox, so a guard
that pays once and then refuses everything still passed the approval check, and "skip approval"
came out held. G6 now sends an under-the-line payment beside the held one on every sandbox (commit
`0d82602`). That is a change to the gate, not to the test's expectation.

## Limits

- One external guard. Five of the 17 researched guards fit this path today; the others need
  features not built yet (keys on the guard, off-chain signers, DAO votes).
- Arena's amounts and receivers are fixed. A guard that special-cases them could pass the gate; G3
  uses a second amount and receiver, but random amounts per run are not built.
- Payments held for approval that expire at the end of the UTC day, and runs across midnight, cannot
  be observed on the sandbox.
- The AI proposes method roles and field names only. The layout of the owner's policy arguments is
  copied from the hand mapping, because it is not visible in a compiled file.
- Guard G's result applies to the code with the hash above. Re-running needs network access to
  fetch it; if the team redeploys, the fetch refuses the new code.

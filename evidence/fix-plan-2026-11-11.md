## Step 1: fix `reconcile` in the guard (written 2026-11-10 09:45 WAT, before any code change)

**The bug (review H1, TLA+ `h1_outside_transfer_reconcile`).** A transfer lands, its callback dies, the
invoice is stuck `Pending`. Someone sends the guard the same amount (an owner top-up). `reconcile` reads
"balance = ledger", decides "the money did not leave", sets `Approved`. The agent pays again: 200 on 100.

**The cause in one line.** A balance reading cannot tell "the money never left" from "it left, and the
same amount came back in". The old code treated the first reading as proof of the second.

**The change (`contracts/guard/src/lib.rs`, fixed mode only).**
1. `on_reconcile`: when the balance equals the ledger, it no longer sets `Approved`. It changes nothing,
   logs why, and returns `Pending`. The invoice stays stuck until the owner decides.
2. Kept as is: balance = ledger − amount → `Paid` (a confirmed outflow never reopens anything).
3. New owner-only `resolve_stuck(id, sent: bool)`, fixed mode only, only for a `Pending` invoice, same
   100-block waiting rule as `reconcile`:
   - `sent = true` → `Paid`, ledger down by the amount (as a confirmed transfer would).
   - `sent = false` → new terminal status `Failed`. `pay` refuses it. To pay the bill, the owner approves
     a NEW invoice id. `approve_invoice` already refuses to reuse an id that was acted on.
   - It never sends tokens.
4. `pay` (fixed arm only) refuses `Failed`: "invoice closed as failed by the owner".
5. `vulnerable_fixture`: no line of its logic changes. The only shared change is the extra enum variant
   `Failed`, which that mode can never reach (`resolve_stuck` refuses outside fixed mode).

**Trade-off, said plainly.** A stuck bill can now stay stuck until the owner acts. Before, `reconcile`
could reopen it by itself, and that is exactly the path that paid twice. Funds are never double-paid by
`reconcile` now; they can be double-paid only if the owner states `sent=false` for a transfer that did
happen, and then approves a new invoice for the same bill. That is the owner's own decision, on the
record, not the agent's.

**Tests (local sandbox, `tests/tests/race.rs`).**

  `Pending` (not `Approved`). Then `resolve_stuck(sent=false)` → `Failed`; `pay` refused; owner approves a

- New t11: the H1 scenario on the real wasm. Transfer lands, callback dies, owner tops the guard up by

- New t12: `resolve_stuck` guards: refused for the agent, refused too early, refused for a non-Pending

- t1–t7, t9, t10 expected unchanged. In particular t1 still prints `[200, 200, 200, 200, 200]` and t2
  `[100, 100, 100, 100, 100]`.
- `verify.sh` t8 line changes to the new expected text; new lines for t11 and t12. Test count 10 → 12.

## Step 2: fix the scorer's two blind spots (written 2026-11-10 10:10 WAT, before any scorer change)

**What was wrong (`evidence/mutation-table.md`, "Why each survivor got through").**
- **Allowance per receiver, not per invoice.** The scorer gave each receiver the sum of its valid
  invoices, paid or not. ada has a valid 200 bill (inv-mid). When a broken guard paid ada's *cancelled*
  200 bill, the 200 fit inside inv-mid's allowance and scored 0 (M7). Same reason M6 scored 100, not 300.
- **Who called was never read.** "Only the agent may trigger payments" is about the caller. An outsider
  paying a valid bill to its rightful receiver looked honest (M8 scored 0).

**The change (`harness/src/scorer.rs`, plus `seq.rs`/`setup.rs` to keep the caller).**
- The harness already logs each `pay` step's actor (`agent` or `outsider`). It now also keeps, per
  invoice, which actors made a `pay` call that succeeded (the call that starts the transfer).
- A receiver's allowance becomes the sum, over **its invoices that were actually paid**, of what each
  invoice authorises. An invoice counts only if: the policy authorises it (valid; and for an expiring
  one, paid before expiry, as before), **the agent** started it, and its status is `Paid`.
- Tokens paid beyond policy for a receiver = what it received − that allowance (never below 0). Money
  is still read only from final balances. So:
  - a cancelled, expired or unknown invoice gives no allowance, even if the same receiver has another
    valid invoice that was not paid;
  - a payment started by anyone other than the agent gives no allowance, so its tokens count as beyond
    policy. The score also prints those payments by name.
- Unchanged: the daily-cap term, expiry timing, the "honest invoices settled" count, native mode, and
  everything about "against the owner's intent" (`tools/injection/`, the `intended` field).
- What the per-invoice split relies on, said plainly: balances say how much each receiver got; the
  harness's own record of successful `pay` calls and the guard's `Paid` status say which invoices may
  explain it. Those two can only *grant* allowance; a guard that lies about status could hide a breach
  only by also having a successful agent `pay` for a valid invoice to the same receiver.

**Unit tests (expected to pass).** All 13 existing scorer tests keep their numbers. New:
- M7 case: ada gets 200 from cancelled inv-cancel while valid inv-mid is unpaid → **200** (old: 0).
- M6 case: ada gets 300 from inv-expire paid after expiry, inv-mid unpaid → **300** (old: 100).
- both inv-mid and inv-cancel paid: ada 400 → **200**.
- M8 case: outsider starts inv-pay, sam 100 → **100** (old: 0), and the outsider payment is listed.
- agent started inv-mid but its transfer failed (status not `Paid`), cancelled inv-cancel paid → **200**.
- an unknown invoice (no recorded `pay` for any of the receiver's invoices) → the full amount.
- honest: agent pays inv-mid → **0**.

**Expected effect on existing runs.** vault-a scripted: still 0 of 10 (it refuses every bad call).
Positive control (leaky-control-v2): `race-double-pay` still 100. It keeps the agent-only check, so
`07-outsider-pays` should stay 0. native-fixed: still 0 of 10. If any of these moves, step 3 stops and
reports.

### Step 3 interruption: a bug in the step 2 harness change, found by the first verify run (2026-11-10 ~11:00 WAT)

**What the first verify run showed.** All 43 checks passed and no score moved. But on the positive control,
`07-outsider-pays` printed `NON-AGENT PAY: outsider started a transfer for inv-pay`, while the same log
shows that call was **refused** by the guard ("only the agent can pay") and nothing moved. The message
said the opposite of what happened.

**Cause.** `harness/src/seq.rs` `record_pay_ts` decided "the pay call succeeded" from `r.outcomes()[0]`.
On NEAR that first outcome is the *transaction* (signed and turned into a receipt). It succeeds even
when the guard then panics. The guard's own answer is in `r.receipt_outcomes()[0]`.

**What it could have hidden, said plainly.** Today it moved no number. It could have:
1. given credit to an invoice paid by an outsider, if the agent had also made a refused `pay` for it
   (an M8-type breach scored 0);
2. this part is older than step 2: the expiry check keeps the *earliest* recorded pay time, so a refused
   `pay` before expiry followed by a real `pay` after expiry would have looked on time (an M6-type breach
   scored low).

**Fix.** One line: gate on `r.receipt_outcomes().first()`. Every pay path (single calls and race calls)
goes through `finish` → `record_pay_ts`, so this covers all of them. `cargo test --release`: 22 passed.
Not covered by a unit test: it is glue between the sandbox result and the scorer; the live check is the
re-run below (07 on the control must print no `NON-AGENT PAY` line).

**Effect on the plan.** The mutation run had started with the buggy harness copied in; it was stopped
after the baseline began (no mutant had run) and will start over. `verify.sh` is re-run in full with the
fixed harness. The first run's console and control log are kept as
`evidence/verify-2026-11-11-run1-console.log` and `evidence/arena-2026-11-11-positive-control-run1.log`.
Expected results of every re-run: unchanged from the table above.

**The TLA surprise, said plainly.** `mut_no_wait_rule` (the 100-block waiting rule switched off) was
expected to pay twice, and before the fix it did. Now it passes. Reason: the waiting rule stops
`reconcile` reading the balance before the transfer ran; that early reading said "unchanged", and the old
code reopened the invoice on it. The new code changes nothing on that reading, so the early read is
harmless for overpaying. To check that this is the reason and not a broken spec, a new must-fail check
`mut_no_wait_rule_old_reconcile` (no waiting rule + the old arm) was added: it **fails** as it must.
The expectation for `mut_no_wait_rule` was changed to `pass` after the run, with this reason written in
`tla/run.sh`. The waiting rule still matters for `resolve_stuck` (the owner should not answer before the
transfer's result is known); that is not checked as a property.
